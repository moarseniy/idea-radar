# Веб-поиск: сервис поиска и провайдеры

Радар берёт источники из двух каналов.

1. **Общий веб-поиск** — сервис поиска `app/search`. Раньше этот канал был доступен только через
   веб-плагин облачной LLM и не работал в локальном режиме. Теперь провайдер выбирается в `.env`.
2. **Специализированные коннекторы** — `app/radar/open_sources.py` и `research_apis.py`:
   - новости Bing по каждому языку и GDELT;
   - наука: Crossref и arXiv; OpenAlex отключён по умолчанию (`OPENALEX_ENABLED=1` включает его и резерв arXiv);
   - гранты NIH и CORDIS, закупки TED;
   - GitHub, Hugging Face, патенты FPO, Хабр.

   Они не зависят от провайдера поиска и включаются настройкой `RADAR_OPEN_SOURCES=1`; отдельные коннекторы могут иметь собственные переключатели.

## Провайдеры

| `SEARCH_PROVIDERS` | Что это | Нужны | Фильтр дат у провайдера | Текст страницы |
|---|---|---|---|---|
| `searxng` (по умолчанию) | Свой инстанс метапоиска: Bing, Brave, Google CSE, Mojeek, Яндекс… | контейнер `searxng` из Compose | относительный (`time_range`) | нет |
| `tavily` | Tavily Search API | `TAVILY_API_KEY` | диапазон дат | нет |
| `exa` | Exa, нейропоиск | `EXA_API_KEY` | диапазон дат публикации | да |
| `brave` | Brave Search API | `BRAVE_API_KEY` | диапазон (`freshness`) | нет |
| `yandex` | Yandex Search API v2 (Yandex Cloud); лучшая выдача по-русски | `YANDEX_SEARCH_API_KEY`, `YANDEX_FOLDER_ID` | нет | нет |
| `openserp` | Свой инстанс OpenSERP — скрейпер Bing, DuckDuckGo, Яндекса | `docker compose --profile openserp up` | диапазон (`date`) | по запросу |
| `openrouter` | Веб-плагин OpenRouter: LLM ищет и цитирует ссылки | `OPENROUTER_API_KEY` | нет | нет |

Как устроена работа провайдеров:
- **Цепочка.** `SEARCH_PROVIDERS=brave,searxng` — сначала Brave. Если у него нет ключа, он упал,
  упёрся в лимит или ничего не нашёл, работает SearXNG. `SEARCH_MODE=fanout` вместо этого
  опрашивает всех сразу и объединяет выдачу без повторов URL.
- **Дата оценки.** Результаты, опубликованные позже неё, отбрасывает сервис — независимо от того,
  умеет ли провайдер фильтровать сам. Результаты без даты остаются, их дату потом проверяет чтение
  страницы.
- **Текст страницы.** Если провайдер его отдал (Exa), радар берёт этот текст как документ и не
  скачивает страницу. Цитаты сверяются с этим текстом.
- **Кэш.** Ответ кэшируется по провайдеру и запросу на `SEARCH_CACHE_HOURS` часов. Для платных
  провайдеров повторные прогоны не тратят кредиты.
- **Аудит.** По каждому запросу видно, какой провайдер ответил, сколько нашёл, был ли ответ из
  кэша и какая ошибка случилась у остальных. В интерфейсе это таблица каналов поиска, строка
  «Веб-поиск (провайдер)».

## Запуск

Сервис — отдельный контейнер `search`: `uvicorn app.search.server:app`, порт 8090. Ключи
провайдеров передаются только ему. Радар ходит в него по `SEARCH_URL`, в Compose этот адрес
задан автоматически. Без `SEARCH_URL` тот же код выполняется прямо в процессе радара, так удобнее
при разработке.

```bash
docker compose up --build                       # радар + PostgreSQL + сервис поиска + SearXNG
curl http://localhost:8888/search?q=test\&format=json   # SearXNG напрямую (отладка)
```

API сервиса:
- `POST /search {"text", "as_of", "language", "limit", "lookback_days"}` возвращает результаты и
  аудит провайдеров;
- `GET /health` показывает цепочку провайдеров и настроены ли они; ключи не отдаются.

Если задан `SEARCH_SERVICE_TOKEN`, `/search` требует заголовок `X-Search-Token`.

`RADAR_WEB_SEARCH` выбирает, откуда радар берёт общий веб-поиск:
- `service` — сервис поиска, по умолчанию;
- `llm` — прежний веб-плагин облачной LLM;
- `off` — только специализированные коннекторы.

## Доклады, подкасты и транскрипты

Для исходной темы запускается широкий проход по всем 14 приоритетным локалям: максимум 2 результата
на язык в общем веб-поиске и специализированном поиске докладов/транскриптов. Для дополнительных
веток используются русский, английский и язык исходного запроса (до 3 результатов на язык).
`SEARCH_MAX_QUERIES` остаётся лимитом по умолчанию для остальных задач и проверок; широкий стартовый
проход задаёт локальный лимит на задачу. Это даёт многоязычное обнаружение с ограниченным числом
результатов, а не 14×6 неограниченных выдач.

Найденные страницы проходят общий fetcher, извлечение кандидатов и проверку дословных цитат.
Фактическое число запросов по каждому каналу записывается в аудит поиска.

Поддерживаются опубликованные текстовые страницы, прямые VTT/SRT/TXT/JSON-транскрипты и RSS/Atom
ленты подкастов с тегом `podcast:transcript`. Если страница эпизода сама ссылается на RSS, радар
пытается сопоставить запись по URL или названию и взять расшифровку из RSS. В тексте сохраняются
таймкоды и имена говорящих при наличии; карточка источника показывает формат/происхождение
транскрипта; если RSS содержит enclosure аудио, таймкод может открыть его на нужном месте.

YouTube используется для обнаружения и ссылки на видео. Произвольные страницы YouTube не
скачиваются и не скрейпятся: официальный API не отдаёт текст субтитров без прав владельца канала.
Поэтому сначала ищутся официальная стенограмма организатора, открытый VTT/SRT или копия доклада
в университетском/конференционном архиве. Видео YouTube без доступного текста остаётся найденной
ссылкой, но его речь не передаётся в извлечение кандидатов.

### Необязательное ASR

Для RSS-аудио без готового транскрипта можно настроить собственный OpenAI-compatible
`/v1/audio/transcriptions` endpoint (например, локальный Whisper). По умолчанию ASR выключен.
Нужно указать `RADAR_AUDIO_TRANSCRIPTION_URL`; разрешённые домены аудио отдельно перечислить в
`RADAR_AUDIO_TRANSCRIPTION_ALLOWLIST` через запятую. Allowlist — явное подтверждение команды, что
записи этих хостов разрешено отправлять на распознавание. YouTube и `youtu.be` заблокированы для
загрузки/ASR независимо от allowlist. Максимальный файл задаётся `RADAR_AUDIO_TRANSCRIPTION_MAX_MB`
(1–25 МБ), таймаут — `RADAR_AUDIO_TRANSCRIPTION_TIMEOUT` (15–600 секунд). В базу сохраняется
расшифровка и её происхождение, бинарный аудиофайл не кэшируется.

В карточке источника исходная запись остаётся первичным URL; расшифровка показывается как текст
с таймкодами. Автоматическая транскрибация фиксируется отдельно от субтитров, опубликованных
автором. Заявление докладчика само по себе не подтверждает факт внедрения — радар ищет независимые
подтверждения в обычных источниках.

## Проверено

| Провайдер | Как проверен |
|---|---|
| searxng | Живой контейнер, весь стек в `docker compose` (радар → `search` → `searxng` по сети Compose), полные прогоны радара — ниже |
| tavily | Один живой запрос: 5 результатов за 3 с (кредиты берегутся) |
| openrouter | Живой запрос: 5 ссылок из цитат за 10 с |
| openserp | Живой контейнер (`--profile openserp`): `/mega/search`, 5 результатов за 11 с; ответ — объект с `results` |
| exa, brave, yandex | Тесты на записанных ответах по документации API (`tests/test_search_service.py`); ключей у команды нет — живую проверку сделать при их появлении |

**Полный прогон радара** «Слабые сигналы в финансовых технологиях для банков», LLM в облаке
(`openai/gpt-4.1`). Сравнивались два способа веб-поиска на одном и том же коде:

| Веб-поиск | Ссылок найдено | Прочитано (из них веб-поиск) | Кандидатов | Подтверждённых сигналов | Время |
|---|---:|---:|---:|---:|---:|
| сервис поиска, SearXNG (HTTP-сервис по `SEARCH_URL`) | 506 | 47 (4) | 17 | 5 | 4,8 мин |
| веб-плагин LLM (`RADAR_WEB_SEARCH=llm`) | 476 | 48 (4) | 15 | 6 | 5,9 мин |

Сервис поиска с бесплатным SearXNG работает наравне с веб-плагином LLM, не тратит токены и
доступен в локальном режиме.

При этом в обоих случаях из веб-поиска прочитано только 4 из ~48 документов. Бюджет чтения почти
целиком уходит на специализированные коннекторы: у них больше 500 ссылок на 14 языках, а
структурным источникам отведены отдельные места в очереди. Отсюда и шумные кандидаты в обоих
прогонах: «stochastic resonance», «Raman-сенсоры для биометрии», «мониторинг OpenAlex». Балансировку
бюджета чтения между каналами стоит пересмотреть отдельно.

**Что выяснилось при прогоне в Docker.** SearXNG с одного IP упирается в лимиты самих поисковиков.

Первый прогон в Compose отправил около 100 запросов: 14–15 языков на ветку плюс проверочные.
После этого:
- Brave и Google CSE ответили «too many requests», и SearXNG приостановил эти движки;
- DuckDuckGo и Qwant начали отвечать капчей;
- выдача по большинству запросов стала пустой: 32 ссылки на весь прогон.

Сделано три исправления:
- **`SEARCH_MAX_QUERIES=3`** — не больше трёх языков на задачу: русский, английский и первый
  из остальных. Остальные языки покрывают коннекторы Bing News и Crossref. Все проверочные
  запросы по кандидатам сохраняются. Для платных провайдеров это ещё и экономия кредитов.
- **`SEARCH_MIN_INTERVAL=1.0`** — пауза между запросами к своему SearXNG или OpenSERP.
- **`SEARXNG_ENGINES`** — явный набор движков, по умолчанию `yahoo,bing news,google news,brave,google cse,duckduckgo`.
  Проверено по одному движку с того же IP: Yahoo, Bing News и Google News продолжают давать по
  7–10 результатов, когда Brave и Google CSE уже приостановлены. Bing (web), Mojeek, Startpage,
  Presearch и Marginalia в настройках по умолчанию не активны или пусты. У Яндекса ломается
  разбор выдачи.

| Прогон в Compose («финтех для банков») | Ссылок из веб-поиска | Задач с выдачей | Прочитано из веб-поиска | Сигналов |
|---|---:|---:|---:|---:|
| до исправлений | 32 | 3 из 8 | 3 из 43 | — |
| после исправлений | 126 | 7 из 7 | 9 из 49 | 7 |

**Режим `local` целиком.** Проверен запрос «Новые технологии защиты ИИ-агентов в банках».
Ollama не использовалась: роль локального сервера играл OpenRouter с Qwen3.6-35B-A3B без рассуждений.
Веб-поиск — сервис поиска с SearXNG.

- 590 ссылок, из них 144 из веб-поиска; 42 документа прочитано.
- 22 кандидата, 11 из них подтверждены как слабые сигналы; в ТОП-15 все 15 по теме.
- 21 вызов LLM, ни одного сбоя.
- Модель скоринга `logreg_v1_qwen3.6-35b-a3b.json` выбрана автоматически по имени LLM.
- Время — 12,8 мин.

До появления сервиса поиска в этом режиме было подтверждено 6 сигналов (docs/10-model-comparison.md).

Для стенда, которым пользуются часто, надёжнее ставить в цепочку платный API впереди SearXNG,
например `SEARCH_PROVIDERS=brave,searxng`: у Brave Search API есть бесплатный лимит.

Для русскоязычной выдачи лучше всего подходит `yandex` (Yandex Search API) в цепочке перед
SearXNG.

## Локальная LLM: Ollama, vLLM, SGLang

`RADAR_PROVIDER=local` работает с любым OpenAI-совместимым сервером. `LOCAL_LLM_BACKEND` задаёт,
как у сервера выключаются рассуждения:

| Сервер | `LOCAL_LLM_URL` | `LOCAL_LLM_BACKEND` | `LOCAL_MODEL` | Рассуждения выключаются |
|---|---|---|---|---|
| Ollama | `http://localhost:11434/v1` | `ollama` | `qwen3.6:35b-a3b` | `reasoning_effort: none` |
| vLLM | `http://localhost:8000/v1` | `vllm` | `Qwen/Qwen3.6-35B-A3B` | `chat_template_kwargs.enable_thinking=false` |
| SGLang | `http://localhost:30000/v1` | `sglang` | `Qwen/Qwen3.6-35B-A3B` | `chat_template_kwargs.enable_thinking=false` |
| другой (LM Studio…) | свой | `openai-compatible` | свой | задайте `LOCAL_LLM_EXTRA` |

Ещё несколько деталей:
- **Блок `<think>…</think>`.** Если сервер запущен без reasoning-парсера, этот блок приходит прямо
  в ответе. Он вырезается до разбора JSON.
- **Модель скоринга по HF-id.** Для HF-id (`Qwen/Qwen3.6-35B-A3B`) выбирается та же модель
  скоринга, что для `qwen3.6:35b-a3b`.
- **Профили Compose.** `ollama`, `vllm` и `sglang` поднимают сервер одной командой, например
  `docker compose --profile vllm up`. vLLM и SGLang требуют NVIDIA GPU. Их проверка ограничена
  тестами на формат запроса и документацией: на MacBook M5 их не запустить. Живьём проверена
  Ollama (docs/10-model-comparison.md).
