# Методология выявления слабых сигналов

Документ задаёт актуальную постановку классификации, правила исключения, модель, разметку и протокол оценки. Канонический реестр признаков находится в [05-features.md](05-features.md), инструкция разметчика — в [06-labeling-protocol.md](06-labeling-protocol.md).

## 1. Определение

Слабый сигнал на дату `t` — конкретная технология в конкретном применении, для которой одновременно наблюдаются:

1. ранняя стадия: исследование с переходом к прототипу, PoC, пилот или первые ограниченные внедрения;
2. значимое новое изменение: технический результат, рост активности, снятие барьера, первый пилот или новая область применения;
3. потенциальная практическая значимость;
4. проверяемые технические свидетельства;
5. отсутствие подтверждённого массового распространения и сформированного рынка именно рассматриваемого применения.

Рабочая формула:

```text
слабый сигнал = ранняя стадия × положительная динамика × технические свидетельства × ограниченная зрелость
```

Низкая известность сама по себе не является сигналом. Старое нишевое решение, один пресс-релиз и отсутствие результатов поиска не должны становиться позитивами.

Единица классификации:

```text
technology_application_id × snapshot_date
```

Одна технология может быть позитивом в раннем временном срезе и негативом после масштабирования.

## 2. Что показывает Excel организаторов

В 100 строках присутствуют только положительные примеры. Поля «Стадия развития» и «Тренд упоминаний» позволяют восстановить авторскую рубрику:

```text
Балл = стадия (1..4) + тренд (1..3)
```

| Стадия | Балл | Тренд | Балл |
|---|---:|---|---:|
| Концепция/исследование | 1 | Стабильный | 1 |
| Прототип/PoC | 2 | Растёт | 2 |
| Пилот | 3 | Растёт быстро | 3 |
| Раннее внедрение | 4 |  |  |

Это полезная методическая подсказка и позитивный benchmark. Таблица не содержит отрицательного класса и не является независимым бинарным test set после изучения командой. Авторский балл и объяснение запрещены как признаки.

Стадия и тренд, размеченные людьми, сохраняются как вспомогательные поля для анализа ошибок. Основная модель не пытается воспроизводить их отдельными головами: в текущем объёме применяется одна бинарная логистическая регрессия по воспроизводимым признакам.

## 3. Жёсткие ворота

Ворота применяются до модели, когда условие подтверждено источником. Пороговые правила версионируются; решение сопровождается причиной и evidence ID.

| Код | Условие | Результат |
|---|---|---|
| G1 Зрелость | Массовое внедрение, обязательный/широко применяемый финальный стандарт или доказанный массовый рынок именно применения | исключить как зрелое |
| G2 Не технология | Компания, отдельный бренд, персона, общее направление или рыночное событие без технологического содержания | исключить как нерелевантное |
| G3 Нет технического свидетельства | Только реклама/перепечатки, нет статьи, патента, технической документации, репозитория, пилота или измеримого результата | исключить как хайп/шум |
| G4 Недостаточно данных | Невозможно подтвердить раннюю стадию или датировать ключевые события | отказ от решения, не принудительный негатив |
| G5 Временная утечка | Единственное основание опубликовано после `snapshot_date` | исключить основание; пересчитать или отказаться от решения |

Наличие финального стандарта не всегда означает зрелость узкого нового применения. Ворота применяются к объекту `технология + применение`, а не к широкому базовому термину.

Жёсткое требование двух источников для любого позитивного объекта не вводится: качественная первичная научная работа может быть единственным свидетельством действительно раннего результата. В таком случае качество доказательств и ограничение показываются явно. Перепечатки одного анонса не считаются независимыми подтверждениями.

## 4. Признаки

Канонический пул содержит **63 логических признака-кандидата в семи блоках**:

1. стадия, внедрение и зрелость;
2. научная динамика;
3. патентная динамика;
4. медиа и качество доказательств;
5. финансирование;
6. текст и семантика;
7. межканальные признаки;
8. пять индикаторов пропусков учитываются отдельно в том же пуле.

Финальная модель должна содержать ориентировочно 18–25 признаков после отбора внутри CV.

Принципы:

- числовые counts, суммы и даты берутся из API/реестров, не генерируются LLM;
- LLM разрешён только для чтения текста и категориального извлечения со строгой схемой, версией промпта и подтверждающей цитатой;
- DOI, патентные семейства, перепечатки и события дедуплицируются до расчёта;
- значение, формула, окно, snapshot date, source IDs и версия aliases сохраняются;
- пропуск не заменяется фактическим нулём.

## 5. Основная модель

### 5.1 Pipeline

```text
жёсткие ворота
  → расчёт 63 кандидатов
  → train-only imputation / scaling / bins / one-hot
  → отбор признаков внутри вложенной CV
  → LogisticRegression L2
  → калибровка на отдельной части
  → вероятность + вклады признаков
```

Baseline — `sklearn.linear_model.LogisticRegression` с L2-регуляризацией. `class_weight` используется только после выбора целевой функции и анализа реальной распространённости класса.

Немонотонные признаки преобразуются bins или spline внутри pipeline. Иначе линейная модель не выразит главное свойство слабого сигнала: нулевой объём означает отсутствие свидетельства, промежуточный — раннюю активность, высокий — возможную зрелость.

### 5.2 Контрольные модели

Для доказательства ценности признаков сравниваются:

1. константный/DummyClassifier baseline;
2. правила по стадии и росту;
3. TF-IDF + логистическая регрессия по допустимому тексту;
4. LLM zero-shot;
5. основная логистическая регрессия на структурированных признаках.

Более сложная модель рассматривается только после baseline. Если прирост небольшой, линейная модель предпочтительнее из-за интерпретируемости.

### 5.3 Интерпретация

Для физической колонки:

```text
contribution_j = transformed_feature_j × coefficient_j
```

Пользователь видит сначала вклад семи блоков, затем 3–5 крупнейших положительных и отрицательных признаков с исходными значениями и источниками.

Коэффициент не является причинным эффектом. Некалиброванный `predict_proba` не называется уверенностью. После калибровки показываются Brier score, calibration curve и границы применимости.

## 6. Обучающая выборка

### 6.1 Ярусы

| Ярус | Происхождение | Использование |
|---|---|---|
| Позитивный benchmark | 100 строк организаторов | проверка покрытия позитивов и анализ согласованности; не бинарный holdout |
| Серебро | реальные позитивы и негативы, два независимых аннотатора | обучение и nested CV |
| Золотой holdout | самостоятельно собранные позитивы и негативы, отложенные до финала | финальные бинарные метрики |
| Бронза | псевдоразметка основной моделью с выборочной ручной проверкой | только дополнительное обучение с малым весом; не метрики |

LLM может предлагать кандидатов, но не ставит финальные метки серебряного и золотого набора.

### 6.2 Негативы

Рекомендуемая структура:

- 30–35% зрелые технологии;
- 20–25% хайп/маркетинг без технического артефакта;
- 40–50% трудные негативы: нишевая зрелость, ребрендинг, растущая массовая технология, исследование без движения, продукт/компания вместо технологии.

Очевидные негативы нужны для smoke test, но не должны доминировать.

### 6.3 Объём

Цель — примерно 300 позитивов и 400 негативов, если позволяет время. При хакатонном ограничении сначала собирается меньший, но качественный набор с сильными near-miss негативами. Число признаков финальной модели ограничивается фактическим размером и стабильностью коэффициентов.

## 7. Источники и доверенность

| Уровень | Типы |
|---|---|
| A | регуляторы, университеты, научные центры, рецензируемые журналы, патентные ведомства, государственные реестры |
| B | конференции, отраслевые ассоциации, аналитические отчёты, профессиональные медиа, техническая документация разработчиков |
| C | корпоративные блоги, пресс-релизы, вендорские материалы |
| D | соцсети, личные блоги, агрегаторы, анонимные и рекламные ресурсы |

Уровень доверенности — свойство источника, не автоматическая истинность каждого утверждения. Для каждого документа сохраняются организация-первоисточник, URL, дата, язык, тип, trust reason, content hash и связь с событием.

## 8. Протокол оценки

| Элемент | Правило |
|---|---|
| Разделение | группы связанных технологий/aliases/событий не пересекают folds |
| Время | финальный holdout позже train; никаких документов после snapshot date |
| Отбор | imputation, bins, scaling, корреляционная чистка и selection только внутри train fold |
| Метрики | Precision, Recall, F1, PR-AUC, balanced accuracy, confusion matrix |
| Калибровка | Brier score и calibration curve |
| Устойчивость | bootstrap-интервалы коэффициентов и метрик |
| Домены | leave-one-domain-out как стресс-тест, если хватает данных |
| Режимы | `offline_features`, `enriched`, `open_search` оцениваются отдельно |

При выборе порога сначала фиксируется цена ошибок. Для ТОП-15 важнее Precision@15 и доля зрелых технологий в выдаче; для скрининга — Recall при заданном бюджете ручной проверки.

Результаты на 100 строках организаторов публикуются как recall/coverage позитивного benchmark, а не Accuracy или F1.

## 9. Защита от утечки

- авторское объяснение, балл, номер строки и количество ссылок Excel не используются;
- evidence для позитивов и негативов собирается одним ETL;
- признаки происхождения файла, разметчика и шаблона исключаются;
- aliases и query templates версионируются;
- features и labels разделены физически;
- все преобразования входят в sklearn Pipeline;
- экспериментальный журнал фиксирует dataset hash, schema version, split seed/groups и commit.
